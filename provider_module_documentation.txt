1. Root Cause of Provider Fetch Failure (User Dashboard):
   - During the previous session's provider dashboard API implementation, the general search helper functions (`get_providers` and `get_provider_by_id`) were accidentally omitted from `backend/app/providers/service.py`.
   - When a logged-in user opened the User Dashboard, the frontend triggered a request to `GET /providers/`. The controller attempted to call `service.get_providers(...)` but failed with `AttributeError: module 'app.providers.service' has no attribute 'get_providers'`.
   - This caused the backend to return an HTTP 500 Internal Server Error, leading to the "Failed to fetch providers" error on the frontend and a provider count of 0.
   - Fix: Added `get_providers` and `get_provider_by_id` back to the service layer, delegating search queries correctly to `repository.py`.

2. Root Cause of Provider Dashboard Blank Page:
   - In `frontend/src/pages/ProviderDashboard.jsx`, the `<User>` Lucide icon component was rendered in the profile summary header (line 486). However, `User` was never imported from the `'lucide-react'` library at the top of the file.
   - This caused a runtime JavaScript `ReferenceError: User is not defined` when the React virtual DOM attempted to render the dashboard layout, halting execution and causing the entire screen to go blank.
   - (Secondary issue): On this Python environment, the `passlib` password hashing package triggered compatibility crashes with the newer `bcrypt` library (throwing `AttributeError: module 'bcrypt' has no attribute '__about__'`). This prevented the backend from verifying passwords during provider login.
   - Fixes: 
     a. Added `User` to the lucide-react import list in `ProviderDashboard.jsx`.
     b. Replaced `passlib.CryptContext` with direct `bcrypt` hashing and verification in `backend/app/config/security.py`, making authentication 100% stable.

   - `frontend/src/services/notificationService.js` (Converted Python-style comments to JS `//` comments to fix Vite build)

--------------------------------------------------
SYSTEM ARCHITECTURE REFERENCE
--------------------------------------------------

1. OVERVIEW
The Provider Module enables registered Service Providers to manage their profile, list service offerings (like Plumbing, Electrical Work, etc.), view incoming booking requests from customers, change the status of bookings (Accept, Reject, Cancel, Complete), receive notifications, and track their total earnings and booking statistics.

2. PROVIDER PROFILE & IDENTITY
- Provider identity is based entirely on the existing "users" collection.
- A provider is simply a registered user with a role of "provider" (or "Provider"). No separate provider collection is created.
- The provider can edit their profile details (Full Name, Phone, Gender, Address, City, State, Pincode, Service Category, Experience, Description, Hourly Rate, and Time Slots Availability).
- Editing this profile modifies the user's document in the "users" collection.

3. PROVIDER AUTHORIZATION
- Provider APIs are secured using the existing JSON Web Token (JWT) system.
- When a provider logs in, their JWT is generated containing their user ID and role ("provider").
- For every provider API request, the FastAPI backend checks:
  1. The Authorization header exists and has a valid Bearer token.
  2. The JWT is successfully decrypted.
  3. The role stored in the token is "provider".
- If a normal user (role = "user") tries to access provider APIs, the backend immediately returns a proper HTTP 403 Forbidden status code.

4. BOOKING STATE LIFECYCLE
A booking always remains the exact same MongoDB document. Changing the status modifies the "booking_status" field rather than inserting new documents.

Supported Transitions:
- Pending → Accepted (Provider clicked Accept Booking)
- Pending → Rejected (Provider clicked Reject Booking + optional reason)
- Accepted → Completed (Provider clicked Mark as Completed)
- Accepted → Cancelled (Provider clicked Cancel Booking + optional reason)
- Pending → Cancelled (Customer cancelled the booking from User Dashboard)

Invalid Transitions (Prevented by backend state check):
- Rejected → Accepted (Blocked)
- Cancelled → Accepted (Blocked)
- Completed → Accepted (Blocked)
- Completed → Cancelled (Blocked)
- Rejected → Completed (Blocked)

5. STEP-BY-STEP FLOWS

A. Booking Creation Flow:
   1. Customer logs in, searches for a provider, and selects a service.
   2. Customer fills booking details (Date, Time, Address, Notes) and clicks "Confirm Booking".
   3. Frontend POSTs payload to `/bookings/`.
   4. MongoDB creates booking document with booking_status = "Pending" and payment_status = "Pending".
   5. Backend creates a notification for the provider ("New booking received from [Customer Name] for [Service Name].").

B. Accept Booking Flow:
   1. Provider views the Pending Request on the Provider Dashboard.
   2. Provider clicks "Accept Booking" and confirms in the dialog.
   3. Frontend sends PATCH request to `/provider/bookings/{id}/accept`.
   4. Backend verifies JWT, provider role, and booking ownership.
   5. Booking status updates to "Accepted".
   6. Backend creates a notification for the customer ("Your booking for [Service Name] has been accepted by [Provider Name].").

C. Reject Booking Flow:
   1. Provider views the Pending Request on the Provider Dashboard.
   2. Provider clicks "Reject Booking", confirms, and enters an optional rejection reason.
   3. Frontend sends PATCH request to `/provider/bookings/{id}/reject` with { "reason": "[reason]" }.
   4. Backend updates status to "Rejected" and saves "rejection_reason".
   5. Backend creates a notification for the customer ("Your booking for [Service Name] has been rejected by [Provider Name]. Reason: [reason]").

D. Cancel Booking Flow (Provider Side):
   1. Provider clicks "Cancel Booking" on an Accepted booking card.
   2. Provider enters a cancellation reason in the modal and confirms.
   3. Frontend sends PATCH request to `/provider/bookings/{id}/cancel` with { "reason": "[reason]" }.
   4. Backend updates status to "Cancelled" and saves "cancellation_reason".
   5. Backend creates a notification for the customer ("Your booking for [Service Name] has been cancelled by [Provider Name]. Reason: [reason]").

E. Complete Booking Flow:
   1. Service is finished. Provider clicks "Mark as Completed" and confirms.
   2. Frontend sends PATCH request to `/provider/bookings/{id}/complete`.
   3. Backend updates status to "Completed".
   4. Backend creates a notification for the customer ("Your booking for [Service Name] with [Provider Name] has been completed.").

6. NOTIFICATION SYSTEM
- Shared collection "notifications" is used to persist alerts.
- Format of notification document:
  {
      "_id": ObjectId,
      "user_id": "[Recipient User ID]",
      "title": "[Title of Alert]",
      "message": "[Descriptive Message]",
      "notification_type": "[BOOKING_CREATED | BOOKING_ACCEPTED | BOOKING_REJECTED | BOOKING_CANCELLED | BOOKING_COMPLETED]",
      "booking_id": "[Associated Booking ID]",
      "is_read": false,
      "created_at": datetime
  }
- Customer reads notifications on the new "Notifications" tab in the User Dashboard. Clicking a notification calls PATCH `/notifications/{id}/read` to mark it as read.
- Provider reads notifications on the "Notifications" tab in the Provider Dashboard.

7. SERVICE MANAGEMENT FLOW (CRUD)
Providers can manage their listing categories:
1. Add Service: Enter Title, Category Name, Price Tier ($, $$, $$$), Price Value (hourly rate), City, and Description. The backend looks up provider name, profile image, and availability from the user document to enrich the service record automatically.
2. View Services: View all services owned by the authenticated provider.
3. Edit Service: Edit any service parameter.
4. Toggle Status: Activate or deactivate service (sets "status" to "active" or "inactive").
5. Delete Service: Completely delete service from MongoDB.

8. COMPLETE LIST OF APIS
- GET /notifications/ : Fetch notifications for the caller.
- PATCH /notifications/{notification_id}/read : Mark a notification as read.
- GET /provider/dashboard : Get stats (Total, Pending, Accepted, Completed, Cancelled, Earnings).
- GET /provider/bookings : List provider's bookings (enriched with customer details).
- GET /provider/bookings/{booking_id} : Get details of a specific booking.
- PATCH /provider/bookings/{booking_id}/accept : Accept pending booking.
- PATCH /provider/bookings/{booking_id}/reject : Reject booking + optional reason.
- PATCH /provider/bookings/{booking_id}/cancel : Cancel accepted booking + optional reason.
- PATCH /provider/bookings/{booking_id}/complete : Mark accepted booking as completed.
- GET /provider/services : List provider's services.
- POST /provider/services : Create a service listing.
- PUT /provider/services/{service_id} : Update a service.
- DELETE /provider/services/{service_id} : Delete a service.
- GET /provider/notifications : Get notifications targeting the provider.
