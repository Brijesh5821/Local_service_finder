================================================================================
LOCAL SERVICE FINDER - USER MODULE DOCUMENTATION
================================================================================

Imagine the application like this simple story:
* Frontend (React) = What the user sees. It is like the storefront of a restaurant.
* Backend (FastAPI) = The waiter who takes the order, talks to the chef, and brings 
  back the food.
* MongoDB = The pantry/fridge where the food (data) is stored.
* Axios = The messenger boy who runs between the frontend storefront and the 
  backend waiter carrying letters.
* FastAPI Router = The reception desk that checks what kind of request came in 
  (e.g., login request, booking request) and sends it to the right person.
* JWT = A temporary entry card stamped by the backend that allows the user to 
  enter private rooms (like the User Dashboard) without showing their ID card 
  (password) every single time.

Let's read this document to understand exactly how the whole User Module works!

================================================================================
BEGINNER-FRIENDLY FLOW OF THE ENTIRE USER MODULE
================================================================================

Let's trace what happens from start to finish when a user uses the platform:

1. **Visiting the website**: The user sees the main website page. The code for this 
   is in React.
2. **Registration**: A new user signs up. They fill in details (name, email, 
   password, role). If they choose the "Provider" role, they also give provider 
   details like their category (e.g., Plumber), hourly rate, and experience. 
   React sends this to FastAPI, which hashes (encrypts) the password and saves 
   it in MongoDB's "users" collection.
3. **Login**: The user enters their email and password. React sends this via 
   Axios to FastAPI. FastAPI checks MongoDB. If they match, FastAPI stamps a JWT 
   token (proof of login) and sends it back. React stores this token in the web 
   browser's memory (LocalStorage) so it remembers who is logged in.
4. **Dashboard**: The logged-in user is redirected to the User Dashboard page. 
   React uses Axios to ask FastAPI for a list of service providers. FastAPI 
   checks MongoDB and returns them.
5. **Searching & Filtering**: The user types a name or selects a filter (like "Plumber" 
   category, "Surendranagar" city, or max price). React sends these filters to 
   FastAPI. FastAPI builds a custom query, pulls the matched providers from 
   MongoDB, and sends them back. React updates the screen.
6. **Booking a Provider**: The user clicks "Book Now". A popup window (BookingModal) 
   asks for the date, time, and address. When they submit, React sends these 
   details with the JWT token to FastAPI. FastAPI verifies the token, creates a 
   booking document in the "bookings" collection in MongoDB with a "Pending" status, 
   and returns success. React updates the screen to show the new booking.
7. **Logout**: When the user clicks Logout, React deletes the JWT token from the 
   browser's LocalStorage and redirects the user to the Home Page.

================================================================================
EXPLAIN EACH FILE IN SIMPLE LANGUAGE

Below is the explanation for all the important files in this project.

--------------------------------------------------------------------------------
1. File: frontend/src/api/axios.js
--------------------------------------------------------------------------------
* What is this file?
  This is the messenger's setup file. It configures Axios (our messenger).
* Why do we need this file?
  To tell the frontend where our FastAPI backend is running and to automatically 
  attach the user's logged-in token (JWT) to every request.
* What does this file do?
  It sets up a base URL (like "http://127.0.0.1:8000"). It also uses an "interceptor" 
  which is like a postman who automatically stamps the JWT token onto the envelope 
  before sending any letter to the backend.
* When is this file used?
  Every single time the frontend needs to communicate with the backend.
* Which file calls/uses this file?
  All frontend services: `authService.js`, `bookingService.js`, `providerService.js`, 
  and `apiService.js`.
* Which API does it call?
  None directly. It configures the tool that calls all APIs.
* What data does it receive?
  It reads the token from the browser's `localStorage.getItem('token')`.
* What data does it send?
  It attaches `"Authorization": "Bearer <token>"` to request headers.
* Where does that data go next?
  To the FastAPI backend server.

--------------------------------------------------------------------------------
2. File: frontend/src/context/AuthContext.jsx
--------------------------------------------------------------------------------
* What is this file?
  This is the security guard and memory card for the user's login state.
* Why do we need this file?
  To share the logged-in user's details (like name, email, and role) across all 
  components in the app so they know if someone is logged in.
* What does this file do?
  It provides `user` state, `login` function, and `logout` function. When a user 
  logs in, it saves the token in the browser's `localStorage` and decodes it to 
  read user details. It also calls `/users/profile` to get the latest profile data.
* When is this file used?
  Whenever the app starts, or when a user logs in, logs out, or when pages need 
  to check who is logged in.
* Which file calls/uses this file?
  Used in `App.jsx`, `AppRoutes.jsx`, `Navbar.jsx`, `LoginPage.jsx`, and dashboards.
* Which API does it call?
  It calls `GET /users/profile` to get fresh profile data.
* What data does it receive?
  It receives the JWT token from `LoginPage.jsx` or the browser's local storage.
* What data does it send?
  It exposes the `user` object to all child components.
* Where does that data go next?
  It goes to React components like `Navbar.jsx` to render the user's name.

--------------------------------------------------------------------------------
3. File: frontend/src/services/authService.js
--------------------------------------------------------------------------------
* What is this file?
  This is the service file handling authentication operations (registration, login, 
  profile loading/updating).
* Why do we need this file?
  To keep all login and registration network requests in one single organized place.
* What does this file do?
  It defines functions: `register` (to sign up), `login` (to sign in), `getProfile` 
  (to fetch profile), and `updateProfile` (to edit profile details).
* When is this file used?
  When submitting register/login forms, when loading the profile page, or when 
  saving profile changes.
* Which file calls/uses this file?
  `LoginPage.jsx`, `RegisterPage.jsx`, `ProfilePage.jsx`, and `AuthContext.jsx`.
* Which API does it call?
  * `POST /auth/register` (Register)
  * `POST /auth/login` (Login)
  * `GET /users/profile` (Get profile)
  * `PUT /users/profile` (Update profile)
* What data does it receive?
  Forms input data (email, password, full_name, phone, address, etc.).
* What data does it send?
  It sends that form data formatted as JSON to the FastAPI backend.
* Where does that data go next?
  To the Axios messenger, which sends it to FastAPI routes.

19. File: backend/app/auth/service.py
--------------------------------------------------------------------------------
* What is this file?
  This is the logic center for signup and login.
* Why do we need this file?
  To check validation rules (e.g. if email exists), hash passwords, and create 
  secure tokens.
* What does this file do?
  * For `register_user`: Checks if email already exists in the database. If not, 
    hashes the password using bcrypt security helper, adds a creation timestamp, 
    and saves it.
  * For `login_user`: Finds the user in MongoDB by email, verifies if the plain 
    password matches the saved hashed password, and generates a JWT token containing 
    their ID, email, role, and name.
* When is this file used?
  During registration and login.
* Which file calls/uses this file?
  `backend/app/auth/controller.py`.
* Which API does it call?
  None.
* What data does it receive?
  The request objects.
* What data does it send?
  Requests user documents from `repository.py` and returns success/fail status to the controller.
* Where does that data go next?
  Back up the chain to controller -> route -> frontend.

================================================================================
EXPLAIN EACH USER FEATURE IN EASY LANGUAGE
================================================================================

Here is the simple explanation of how each user feature works:

1. **Registration**: 
   Lets new users create accounts. The client fills in a form. React validates 
   password matching, bundles fields, and sends them to the `/auth/register` API. 
   FastAPI encrypts (hashes) the password using a hash function so that if the 
   database is hacked, passwords are safe. A new user record is saved in MongoDB.

2. **Provider Registration**: 
   When registering, if the user picks the "Provider" role, the React form shows extra 
   fields: experience, hourly rate, description, availability times, and category 
   (e.g., Plumber). These fields are stored in the same MongoDB "users" collection 
   under the same document, and `role` is saved as `"Provider"`.

3. **Login**: 
   The user enters email and password. React sends this to the `/auth/login` API. 
   FastAPI checks if the email exists. It verifies if the password hashes match. 
   If correct, FastAPI generates a JWT token. The token is sent to the frontend. 
   React saves the token in LocalStorage and sets the global auth state. React 
   then reads the role from the token to redirect the user to `/user-dashboard` or 
   `/provider-dashboard`.

4. **Logout**: 
   When a user clicks Logout, React deletes the JWT token from the browser's 
   LocalStorage. It resets the `user` state to `null`. This logs the user out 
   instantly, and they are redirected to the home page `/`.

5. **User Dashboard**: 
   The User Dashboard loads two kinds of data: a list of providers (fetched from 
   `/providers/` via `providerService`) and a list of bookings made by this user 
   (fetched from `/bookings/my` via `bookingService`). It handles tab navigation.

6. **Provider Search**: 
   The search bar on the user dashboard lets users type names. When they click search, 
   it makes a request to `/providers/?name=<typed_name>`. The backend performs a 
   regex search in the database on `full_name`, returning matching records.

7. **Provider Filters**: 
   Filters let users refine search results. 
   * **Category**: filters providers by their specialty (`provider_category`).
   * **City**: filters providers by the city they live in (`city`).
   * **Price**: filters providers whose `hourly_rate` is less than or equal to `max_price`.
   * **Rating**: filters providers whose rating is greater than or equal to `min_rating`.
   * **Availability**: checks if the provider has schedule entries for that day.
   The backend applies all these filters to query MongoDB in one step.

8. **Service Board**: 
   This is the public board that displays specific services (like "Leak Detection", 
   "Bathroom Sanitization") instead of generic provider profiles. These services 
   are loaded from the "services" collection and shown on `ServicesPage.jsx`.

9. **Booking**: 
   When a user books a service, they fill a form inside `BookingModal.jsx` (date, time, 
   address, instructions). React makes a call to `/bookings/` POST API. The backend 
   records this booking inside MongoDB with a `"Pending"` status. The page then 
   refreshes the bookings tab so the user can track it.

10. **My Bookings**: 
    The "My Bookings" tab fetches bookings matching the current user ID. Because booking 
    documents only store provider IDs, the backend queries the "users" collection to 
    find the provider's full name, category, and photo, and merges this info so 
    React can draw a complete card.

11. **My Profile**: 
    When `/profile` is opened, React calls `/users/profile` to get the logged-in user's 
    latest info. The user can click Edit, change their phone number or address, and 
    click Save. React calls the PUT profile API to save changes to MongoDB.

12. **Settings**: 
    The settings page contains toggles to customize app behaviors:
    * **Notifications**: toggles email confirmations, promotional emails, push alerts, 
      and SMS alerts.
    * **Application**: toggles dark mode, compact view, language, and currency options.
    * **Security**: updates user password.
    Settings options are saved in local React states.

13. **Navbar**: 
    The Navbar stays at the top of the page. It reads the user state from `AuthContext`. 
    If logged in, it parses the user's name (or email if name is missing) and extracts 
    initials (like "JD" for John Doe) to draw an avatar circle. It displays links 
    tailored to the user's login state.

MONGODB EXPLANATION IN EASY LANGUAGE
================================================================================

MongoDB is a document database. Let's understand some basic terms:
* **MongoDB Collection**: This is like a folder or a table in SQL. It stores related cards.
* **MongoDB Document**: This is like a single card or a row in SQL. It is written 
  as a JSON-like object (key-value pairs) inside a collection.
* **ObjectId**: A unique identifier generated automatically by MongoDB for every 
  new document (e.g. `ObjectId("64d1f...")`).

Here are the collections used in this project:

--------------------------------------------------------------------------------
1. users collection
--------------------------------------------------------------------------------
* Why does this collection exist?
  To store account profiles for everyone on the platform (customers, providers, 
  and admins).
* What type of data is stored here?
  * Common fields: `full_name`, `email`, `phone`, `password` (encrypted), `role`, 
    `gender`, `address`, `city`, `state`, `pincode`, `created_at`.
  * Provider-specific fields: `provider_category`, `experience`, `description`, 
    `hourly_rate`, `availability` (object mapping weekdays to time ranges), 
    `average_rating`.
* Which API uses it?
  `/auth/register`, `/auth/login`, `/users/profile`, `/providers/`, `/bookings/`
* Which frontend page uses that data?
  `LoginPage.jsx`, `RegisterPage.jsx`, `UserDashboard.jsx`, `ProfilePage.jsx`, `Navbar.jsx`

--------------------------------------------------------------------------------
2. services collection
--------------------------------------------------------------------------------
* Why does this collection exist?
  To store specific service offerings (like "Full Home Deep Cleaning" or "AC Split Service") 
  linked to provider profiles.
* What type of data is stored here?
  `title`, `description`, `category_name`, `provider_id` (links to the users collection), 
  `provider_name`, `provider_image`, `price` (e.g., "$$"), `price_value` (number), 
  `status` (e.g., "active"), `average_rating`, `city`, `availability`, `created_at`.
* Which API uses it?
  `GET /services/`, `GET /services/{service_id}`
* Which frontend page uses that data?
  `ServicesPage.jsx`

--------------------------------------------------------------------------------
3. bookings collection
--------------------------------------------------------------------------------
* Why does this collection exist?
  To store records of all bookings placed by users.
* What type of data is stored here?
  `customer_id` (user's ID), `provider_id` (provider's ID), `service_id` (can be null), 
  `booking_date`, `booking_time`, `booking_address`, `notes`, `booking_status` 
  ("Pending", "Confirmed", "Completed", "Cancelled"), `payment_status` ("Pending", "Paid"), 
  `total_amount`, `created_at`.
* Which API uses it?
  `POST /bookings/`, `GET /bookings/my`, `PATCH /bookings/{booking_id}/cancel`
* Which frontend page uses that data?
  `UserDashboard.jsx` (My Bookings tab), `BookingModal.jsx`

--------------------------------------------------------------------------------
4. categories collection
--------------------------------------------------------------------------------
* Why does this collection exist?
  To store category names and icons (like Plumber, Electrician) to show on homepages.
* What type of data is stored here?
  `category_name`, `icon` (string representing icons), `image`, `description`, 
  `is_active`, `created_at`.
* Which API uses it?
  Initialized during database initialization in `init_database.py`.
* Which frontend page uses that data?
  `HomePage.jsx` and category lists.

IMPORTANT TERMS - SIMPLE GLOSSARY
================================================================================

* **React**: A Javascript library used to build interactive frontend interfaces.
* **Component**: A reusable building block of the user interface, like a Button or Navbar.
* **Props**: Data passed down from a parent React component to a child component, like parameters to a function.
* **State**: An object that holds active data inside a React component, causing the screen to update when changed.
* **Hook**: A special React function (starting with `use`, like `useState`) that lets you use state and other React features.
* **useEffect**: A React hook used to perform side effects, like fetching data from an API when a page first loads.
* **Axios**: A Javascript library used to make HTTP network requests from the browser to the backend.
* **API (Application Programming Interface)**: A set of routes and rules that lets the frontend communicate with the backend.
* **REST API**: An architectural style for APIs that uses standard web protocols to transfer data.
* **HTTP Method**: The action requested on a route, telling the server what type of operation to perform.
* **GET**: An HTTP method used to read or fetch data from the server.
* **POST**: An HTTP method used to send new data to the server to create a record.
* **PUT**: An HTTP method used to replace or update an entire existing database record.
* **PATCH**: An HTTP method used to make partial updates to a record (like changing one field).
* **DELETE**: An HTTP method used to remove a record from the database.
* **FastAPI**: A fast web framework for building APIs in Python.
* **Router**: A module in FastAPI that groups related API endpoints together (e.g. all `/bookings` endpoints).
* **Endpoint**: A specific URL path on an API (like `/auth/login`) that performs a particular action.
* **Middleware**: Code that runs automatically on every request before it hits the endpoint (e.g. check CORS or tokens).
* **JWT (JSON Web Token)**: A secure, encoded string used as proof that a user is logged in.
* **Authentication**: The process of verifying who a user is (e.g., checking their password).
* **Authorization**: The process of verifying what a user is allowed to do (e.g. checking their role).
* **MongoDB**: A document-based database that stores data in JSON-like records.
* **Collection**: A group of related documents in MongoDB, similar to a table in SQL.
* **Document**: A single record stored in a MongoDB collection, similar to a row in SQL.
* **ObjectId**: A unique 12-byte identifier created automatically by MongoDB for every document.
* **Schema**: A structural blueprint defining what fields are required and what types of data they must hold.
* **Pydantic**: A Python library used by FastAPI to validate that incoming API data matches our defined schemas.
* **CORS (Cross-Origin Resource Sharing)**: A security system that controls which websites are allowed to talk to our API.
* **Environment Variable**: Configuration values stored outside the code (like database links or secrets) inside a `.env` file.
* **CRUD**: An acronym for Create, Read, Update, and Delete—the four basic operations you perform on database records.

HOW TO DEBUG (TROUBLESHOOTING GUIDE FOR BEGINNERS)
================================================================================

--------------------------------------------------------------------------------
1. Problem: Login is not working
--------------------------------------------------------------------------------
* What it usually means:
  The email/password checker failed, the backend server is offline, or the network 
  port is blocked.
* Which file to check:
  * Backend API: [routes.py (auth)](file:///d:/Local-service-finder/backend/app/auth/routes.py) and [service.py (auth)](file:///d:/Local-service-finder/backend/app/auth/service.py)
  * Frontend Login page: [LoginPage.jsx](file:///d:/Local-service-finder/frontend/src/pages/LoginPage.jsx)
  * Configuration: [settings.py](file:///d:/Local-service-finder/backend/app/config/settings.py)
* What to check:
  * Press F12 in Chrome, go to the **Network** tab, click login, and look for `/auth/login`. See if it returns 401 (invalid password) or stays pending (server offline).
  * Check if your backend server terminal is running and listening on port 8000.
  * Check if `SECRET_KEY` is loaded correctly in `.env`.
* How to fix it:
  * If F12 shows a connection error, start the server using `uvicorn app.main:app --reload` inside the `backend` folder.
  * Check the database to see if the user was seeded correctly and you are typing the correct email.

--------------------------------------------------------------------------------
2. Problem: Providers are not showing up on the dashboard
--------------------------------------------------------------------------------
* What it usually means:
  The database query returned an empty list, the MongoDB service is stopped, or the 
  JWT authorization header is missing.
* Which file to check:
  * Backend DB query: [repository.py (providers)](file:///d:/Local-service-finder/backend/app/providers/repository.py)
  * Frontend loader: [UserDashboard.jsx](file:///d:/Local-service-finder/frontend/src/pages/UserDashboard.jsx)
* What to check:
  * Check the F12 Network tab for the `/providers/` call. If it returns 401 Unauthorized, the token was not stored or is expired.
  * Check if the "users" collection in MongoDB contains documents where `role` is `"Provider"` or `"provider"`.
* How to fix it:
  * Log out and log back in to get a fresh token.
  * Run the seeding script `python app/database/seed.py` or restart the backend to run `initialize_database()` to insert default providers.

--------------------------------------------------------------------------------
3. Problem: Booking a provider fails when clicking confirm
--------------------------------------------------------------------------------
* What it usually means:
  The POST request fields do not match the expected API structure, or the backend 
  failed to parse the provider ID.
* Which file to check:
  * Frontend: [BookingModal.jsx](file:///d:/Local-service-finder/frontend/src/components/BookingModal.jsx)
  * Backend logic: [service.py (bookings)](file:///d:/Local-service-finder/backend/app/bookings/service.py)
* What to check:
  * Check the error message in the frontend alert.
  * In the network tab, inspect the payload sent to `/bookings/`. Make sure `provider_id` is a valid 24-character hex string.
* How to fix it:
  * Ensure the provider you are booking exists in the database.
  * Make sure you entered a valid date and time format.

--------------------------------------------------------------------------------
4. Problem: MongoDB data is not appearing on the screen
--------------------------------------------------------------------------------
* What it usually means:
  The backend cannot connect to MongoDB, or the collection has no data.
* Which file to check:
  * Backend Connection: [connection.py](file:///d:/Local-service-finder/backend/app/database/connection.py)
  * Environment variables: `backend/.env`
* What to check:
  * Check your terminal output. If PyMono gives a `ServerSelectionTimeoutError`, the MongoDB server is not running.
  * Verify if `MONGO_URI` in `.env` is correct.
* How to fix it:
  * Start MongoDB locally (open Services on Windows and start MongoDB).
  * Double check the database connection link in your `.env` file (e.g. `mongodb://localhost:27017`).

--------------------------------------------------------------------------------
5. Problem: Frontend gets a 404 error on API calls
--------------------------------------------------------------------------------
* What it usually means:
  The API route path is typed incorrectly on the frontend, or the route prefix is wrong.
* Which file to check:
  * Backend Routes: [main.py](file:///d:/Local-service-finder/backend/app/main.py) and router files
  * Frontend Services: [authService.js](file:///d:/Local-service-finder/frontend/src/services/authService.js)
* What to check:
  * Compare the URL requested by Axios (e.g. `http://localhost:8000/auth/login`) with the route registered in backend files.
* How to fix it:
  * Correct the spelling of the path in Axios request.
  * Check if you forgot to register the router in `main.py` using `app.include_router()`.

--------------------------------------------------------------------------------
6. Problem: Axios gives a CORS error
--------------------------------------------------------------------------------
* What it usually means:
  The API backend is blocking the frontend browser because it is running on a 
  different port.
* Which file to check:
  * Backend Server config: [main.py](file:///d:/Local-service-finder/backend/app/main.py)
* What to check:
  * Look at `origins` array around line 20 in `main.py`. Check if your frontend's port 
    (typically `http://localhost:5173`) is listed.
* How to fix it:
  * Add your exact frontend domain URL to the `origins` list in `main.py` and restart 
    the backend server.
